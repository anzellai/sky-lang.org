# Diagrams that cannot drift

I have drawn a lot of architecture diagrams. Every one of them was a lie within a week.

Not a deliberate lie. The diagram was true when I drew it. Then the code moved — a module grew a database call, an endpoint started reading a field it did not read before, a "we do not log that" quietly became "we log that" — and the diagram did not move, because it lived in a different file, in a different tool, and nothing connected the two. A diagram maintained by hand is a comment maintained by hand: correct at birth, wrong by adolescence, and trusted the whole time.

The compiler does not have this problem. It already holds a complete, current, typed model of the program — every module, every effect, every message, every route, every table. And because a Sky app's `update` is a *pure, total, exhaustively-matched* function, the whole behaviour is statically decidable: the compiler can enumerate every user action, every branch it takes, every effect it fires, every reachable state. So if a diagram is *read from that model*, it cannot drift — there is nothing to keep in sync — and it is *complete*, not a sketch of the parts I remembered. It is a view of the code, generated on demand, the same way [`sky doc`](/blog/if-it-compiles-it-works) generates the API reference from the source instead of from a hand-written table.

So that is what `sky doc --diagram` is. And I have spent a long while making the output good enough to actually submit — not a picture you glance at, but the artefact that stands up in a SOC2 or ISO 27001 review, generated by the person being audited and handed over unchanged. Four diagrams, each answering exactly one question, each read straight from the resolved program. None of them can tell you something the code does not.

They render as a **self-contained SVG** we draw ourselves, with no external tool — the format you actually submit; as **PlantUML** with the default `--format puml`; or as a **table** with `--format md`. `--out` writes to a file. And they adapt to what the app *is* — a Sky.Spa client, a Sky.Live server, a terminal app, or a headless HTTP service — so the trust boundary and its protocol are honest for each shape.

## How a user moves through it

```bash
sky doc --diagram journey
```

This is the behaviour graph, and it is the headline. It draws the app as a **trust-boundary swimlane data-flow diagram**: a browser/client lane holding the pages the user sees, a server lane, a data-store lane, and an external-systems lane. Each page is a state; each action is an edge *out of the page whose own view can dispatch it* — recovered from the view, not guessed — labelled with its lane (a `/_rpc` round-trip or a client-only update), the effect families it reaches, the page it navigates to, and its async continuation (the follow-up message a command fires, drawn `⇢`). It is the map of the product, complete by construction: every message the `update` handles, plus every action a view actually wires up, with dead actions and unreachable states falling out for free.

Two things make it an audit artefact rather than a doodle. It classifies data: a flow is marked **confidential** — a red lock — when it carries a `Secret`, a `Std.Auth` session, or a field whose name reads as personal data, and it *names the reason*, because "trust me" is not evidence. And it names the **external systems** it talks to — the real hosts, read from the actual HTTP calls in your code, not a generic "external API" — which double as your sub-processor list. The lanes adapt to the shape: a Sky.Spa app shows a wasm client crossing `/_rpc`; a Sky.Live app shows a plain browser crossing an SSE event channel; a terminal app has no network boundary at all, and the diagram says so instead of drawing a fake one.

## What crosses the wire

```bash
sky doc --diagram wire
```

This one is **API and call-paths**, and it exists because I got burned by the thing it makes visible. In [an earlier post](/blog/the-tests-i-did-not-write) I described a bug where a split app's generated RPC request silently dropped a field, and the shipping cost came back zero. The request was invisible — I never wrote it, the compiler derived it — so the dropped field was invisible too.

`wire` makes the invisible request visible. It tables every `/_rpc` endpoint and every raw HTTP route with four things: its **access requirement** (does it need the CSRF token, is a `Std.Auth` check on the path — and CSRF-exempt endpoints are *flagged*, because those are the attack surface a review asks about first), its **request** (the model fields that branch reads, plus the message arguments), its **response** (the fields it writes), and the **call-path**: the ordered trace of effects it reaches and the store each one touches. A missing read is now a thing you can *see* in the request column.

It does not stop at `/_rpc`. A raw HTTP endpoint — a Stripe webhook mounted with `App.api "POST /webhooks/stripe"`, say — is charted beside the RPC contract, marked as the CSRF-exempt inbound entry point it is. That is exactly the door a security review knocks on, and it used to be invisible in this picture.

## What the app is made of

```bash
sky doc --diagram components
```

A **C4 container diagram**. It draws the trust boundaries as they actually are: an untrusted browser zone holding the client, a trusted server zone holding the backend, and an external zone for the third parties you call. Inside the server it shows the data stores — with the **real table names**, read from your `Std.Db` schema, not a generic "database" box — the audit-and-logs sink, and an auth marker on the crossing. It makes the client/server split concrete: the pure UI actions that stay in the browser, and the count of effectful actions that cross to the backend. It is derived from the *same effect analysis* the [auto-split](/blog/sky-spa-one-language-every-platform) uses to decide what runs where, so the diagram and the split can never disagree.

## What it knows about you

```bash
sky doc --diagram telemetry
```

A **data-egress inventory**. It lists every place the app tracks or logs something and where that something goes — internal logs, external analytics, consent state — so an auditor reads it as "what behavioural data leaves this system, and to where." Not "here is our privacy policy" — here is, mechanically, every call site in your own code that emits data, complete and current by construction. If you have ever had to answer "what personal data does this service record, and where does it end up," you know that grepping and hoping is not an answer. This is the answer, and it updates itself when the code changes.

## The folder you hand an auditor

The point of all this is not four nice pictures. It is that the pictures are *evidence*, and evidence comes as a package. So:

```bash
sky doc --diagram audit --out audit
```

One command writes the whole pack to a folder: every diagram as an SVG and a Markdown table, plus two evidence documents — a **data inventory** (each store and its data, with the confidential fields named) and a **sub-processor register** (every external system you send data to, with its role). The register is honest in the way an auditor checks for: your own domain is *filtered out* — it is not a sub-processor of itself — and an embedded thing like a YouTube player is separated from a true data processor like a payment provider, because one receives your users' data and the other does not. And an `index.md` maps each file to a named control — SOC2 CC3, CC6, CC7; ISO 27001 Annex A.8, A.9, A.13, A.14, A.15 — so the reviewer knows which requirement each artefact answers.

This site ships its own pack. There is a `diagrams/` folder and an `audit/` folder in the sky-lang.org repository, generated by exactly the commands above, regenerated on release. The architecture documentation for this blog *is* the blog's code, viewed through the compiler.

## The honest line

Each diagram is read-only and conservative by design. It never type-checks beyond the shared load, never lowers, never builds, never writes a file it was not asked to — it looks at the program and reports. Where it cannot be certain — a navigation target computed at run time, a host hidden behind a config constant, an app whose view does not dispatch per page — it *says so*, in the diagram, rather than guessing. A confident wrong answer in a compliance document is worse than no answer, because someone signs it.

That conservatism is the whole point. These artefacts you can trust for exactly one reason: they are not a description of the code kept beside it, they are a view of the code computed from it, over a language whose behaviour is total and therefore fully enumerable. When the code changes, they change. They cannot drift, because there is nothing to drift from.

Run them on your own app — `sky doc --diagram components`, `wire`, `journey`, `telemetry`, or the whole `audit` pack — as an SVG, a table, or PlantUML. Point them at something real and see what your program actually does, as opposed to what you remember it doing.
