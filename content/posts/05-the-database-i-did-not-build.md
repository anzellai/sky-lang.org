# The database I did not build

Three days ago I published a post about two things that did not exist yet. One of them was BlueDB, a data layer for Sky where the model *is* the database. I was careful to say that most of the gates that would tell me any of it was true had not been run, and that the status board was mostly "NOT RUN".

They have been run now. This post is what they said, and what I did about it.

The short version is that the work did not fail. The question changed. Somebody — me, three days later — asked whether a custom storage engine was justified at all, and the answer came back no, with enough behind it that I stopped. What Sky ships instead is PostgreSQL. A real one, built and supervised by the toolchain, across four deployment tiers, arranged so that the application never knows which tier it is in.

That is a smaller claim than the one I made on Wednesday, and a better outcome. The reasoning is the interesting part, so here it is in full.

## What the gates said

The status board is generated by the gate harness and committed, so it cannot be written by hand and it cannot flatter anything. Read today it says: goal 0, the cross-cutting harness goal, FAIL. Goal 2, the one about a unified store with real serializable isolation, FAIL. Goals 1, 3, 4 and 5 — session-bounded state, ease of use, change notification, console access — UNKNOWN, because the gates that would decide them had not run, and a gate that has not run does not get to mean "fine".

Not one goal closed, in six days on the clean-slate rebuild.

The line counts are the part I keep coming back to. That branch added 37,927 lines. The engine itself — the non-test Go under `runtime-go/bluedb/` — was 4,725 of them, twelve and a half per cent. The harness certifying the engine was 48.6 per cent, very nearly four lines of proof for every line of database. And `runtime-go/rt/`, which is where the Sky runtime actually lives, had zero changed lines. Nothing was wired into Sky at all. I had built a very well-audited object sitting next to the language rather than inside it.

The canary did work, for what it is worth. The last post described a deliberately vacuous gate whose only job is to fail if the verification harness ever starts reporting success without checking anything. It reports `VACUOUS` on every run, which is exactly what it is supposed to do, and it is why I trust the FAILs above rather than suspecting the board.

## Why I did not buy one instead

Sky is Apache-2.0 and ships its own runtime inside every binary it compiles, so the constraint on an engine is hard: a permissive licence, and something that embeds into a Go process. Under that constraint I could not find an off-the-shelf engine that gives you genuine serializable isolation.

SQLite is the honest one about it. Its own documentation says: *"SQLite implements serializable transactions by actually serializing the writes. There can only be a single writer at a time."* That is a real guarantee, and it is why SQLite remains a good default for a single-instance app. It is not concurrency.

Pebble is BSD-3 licensed and stays that way, and Pebble is precisely the piece BlueDB had taken — but Pebble is a storage engine, not a transactional database. It gives you ordered bytes, atomic batches and a durable apply. The MVCC, the read-set tracking, the conflict validation, the single-writer committer — the whole part where "serializable" becomes true rather than aspirational — is code you write on top, and it is exactly the code I was writing. Meanwhile CockroachDB itself, the database Pebble was built for, moved to a proprietary licence in November 2024. FoundationDB has the semantics I actually wanted and no embedded mode at all.

So "buy" never resolved to a purchase. It resolved to "take a storage engine and write the hard half yourself", which is not buying. It is building with a head start.

## Why I did not build one either

Which puts the question back: was the hard half worth writing?

I had assumed the demand for it rather than measuring it, so I measured it. Across the entire real-application corpus in the Sky repo — the apps that exist to be exercised the way a user would build them, not the compiler test corpus — there is **exactly one** database transaction. It is in the ledger app, posting a journal entry: one header insert and its two signed lines, in one transaction so a half-written entry can never be observed. It is insert-only. Under READ COMMITTED it would behave identically.

That is the whole demand. One insert-only transaction, in the app whose entire subject is double-entry bookkeeping, which is the most transaction-shaped domain I could have picked on purpose.

Serializable isolation is a genuinely valuable property and I am not arguing otherwise. But I was six days into building an engine for a guarantee nothing in the repository needed yet, with a harness twice the size of the thing it was harnessing, and none of it connected to the language.

## The comparison that settled it

The other assumption underneath BlueDB was that server-driven UI *needs* a reactive database — that the model-database gap I complained about last time is a hole in the architecture rather than an ordinary seam everyone lives with.

That assumption does not survive looking at the field. Phoenix LiveView, Rails with Hotwire, Blazor Server and Livewire all ship production server-driven UI, and all four do it on an ordinary database plus an application-level broadcast. Nobody's database tells the view that a row changed; the code that wrote the row tells the other sessions, and the framework re-renders.

Meteor is the control experiment, because Meteor actually did it the other way. It had database-truth-driven reactivity, it worked, and it turned out to cost on the order of writes multiplied by servers — every write evaluated against every server's live queries. The scaling fix reintroduced the same application-mediated gap the other four had never left.

Sky.Live already has the architecture those four use: server-held session state, sticky routing, in-process pub/sub, and a cross-instance broker for when there is more than one replica. The gap I described is real, and it is a place for a library rather than a reason to write a storage engine.

## What shipped

The principle is one sentence: **the app binary never knows which tier it is in.** It consumes a DSN. What changes across tiers is only who provisions that DSN.

- **Development.** `sky run` supervises a per-project cluster and injects the DSN. Ref-counted, so several `sky run`s of the same project share one cluster and the last one out shuts it down.
- **Production, single app.** `sky build --embed` produces one binary carrying its own PostgreSQL, which it unpacks and starts on first run. One file on a bare host gives you an app and its database.
- **Production, several apps on one host.** `sky db provision --shared` sets up one cluster and hands each app its own role, its own database and its own DSN.
- **Managed or hosted.** The platform injects a DSN, which is what an ordinary managed PostgreSQL already is.

One code path in the app, four provisioning strategies. The binary you test locally is the binary you deploy, which is the whole point of not having a development-only database dialect in the first place.

`--embed` is cheaper than I expected, and I want to be specific because my first guess was badly wrong. The design doc originally estimated 150 to 250 MB. Then it got measured rather than re-estimated: the archive is embedded compressed, so what the binary carries is the gzip and not the extracted tree. On a 7,543,905-byte PostgreSQL 14.21 bundle, the `--embed` binary came out 7,630,720 bytes larger than the same program without the flag — the archive, plus 86,815 bytes of embed metadata and section alignment. A real 25 MB release bundle therefore costs about 25 MB. Embedding costs the archive and essentially nothing else.

The bundles are built from source in Sky's own CI rather than taken from someone else's prebuilt artefacts, with a pinned version, a known configure line and a generated SBOM, and a gate fails the build if a bundle carries anything GPL, LGPL or AGPL. `psql` is deliberately excluded, because it links GNU readline and readline is GPL-3.0 — the server needs `postgres`, `initdb`, `pg_ctl` and the dump tools, not the interactive client. PostGIS, TimescaleDB and Citus are out on the same grounds; pgvector and pg_partman are in, both under the PostgreSQL licence.

## What it costs to run

This is the part I would want to read in someone else's post, so here it is: what one Sky.Live app plus its own PostgreSQL actually needs on one small cloud instance.

- Minimal Linux: about 250 MB.
- The Sky app binary, Go, idle: 30 to 40 MB.
- PostgreSQL base — the postmaster and its six auxiliary processes at `shared_buffers = 32MB`: **36 MB**, measured rather than estimated.
- PostgreSQL backends — one process per *active* connection, 5 to 10 MB each: 40 to 70 MB at six to ten active.
- Sky.Live sessions — one gob-encoded Model per session, typically 10 to 100 KB: about 10 MB at 200 concurrent.

That is roughly **390 MB**, so **1 GB is comfortable** and a free-tier or entry-level instance runs a real Sky.Live app with its own database. The connection ceilings below are ceilings and not allocations — `database/sql` opens lazily, so the host pays for what is in flight.

The counter-intuitive part: **RAM is not the binding constraint. CPU is.** Sky.Live renders views on the server and diffs them on every update, so on a burstable instance the baseline CPU allowance runs out well before the memory does. A 0.25-vCPU-baseline instance is a demo host whatever its RAM says.

And the economic argument for `--embed` is here rather than in the ergonomics. A managed PostgreSQL typically costs about as much again as the small VM next to it. Embedding turns a two-line bill into one, for 36 MB.

Three things bite, and I would rather name them than have you find them:

1. **Backups are the operator's problem.** A single instance has no replica. `sky db provision --shared` generates a backup timer; a single `--embed` app does not get one. "I lost everything" is the failure mode of exactly this setup, and the tooling does not currently prevent it.
2. **Idle sessions evict after five minutes. Active ones do not, and there is no hard cap** on count or bytes. At typical Model sizes that is the 10 MB above and it is irrelevant. An app whose Model carries a large list or a cached dataset is the one way many active sessions exhaust a small host.
3. **Disk.** Data, WAL and the extracted bundle — about 77 MB — is ample on a 30 GB volume and tight on a 10 GB one.

## What it asks of the database

One app process opens four PostgreSQL-facing connection pools — the app's own data, analytics, the Sky.Live session store, and telemetry. The app pool is four connections per CPU, floored at 4 and capped at 32. The three auxiliary pools each take a quarter of that, clamped between 2 and 8, because they do small point work and because the number the server sees is the sum, not any one of them.

- Two cores: 8 for the app, 2 each for the other three. **14 per process.**
- Four cores: 16, plus 4 each. **28 per process.**
- Eight cores or more: 32, plus 8 each. **56 per process.**

PostgreSQL's default `max_connections` is 100. So one eight-core instance at 56 is comfortable, and **two of them are 112, and the second one gets refused.** A cluster that `sky` provisions itself sizes `max_connections` above the app's own ceiling with room for maintenance, but against a stock or managed server the default is what you get.

The before-and-after is the honest half, and it is a defect rather than a feature. Those pools were previously **unconfigured** — Go's `database/sql` zero values, which mean *unlimited* connections and two idle — sitting behind a source comment asserting that the defaults were "already sane". They are not. Unlimited is precisely how an app reaches `FATAL: sorry, too many clients already` under exactly the load it has just scaled up to serve, and unlimited-with-two-idle is also how a pool that briefly grew to twenty throws eighteen connections away and re-dials them on the next burst. That was live in shipped code, it has nothing to do with embedding anything, and it was found while building this. Bounded is much better than unbounded. It is still not the same thing as tuned.

The weak spot, stated plainly: analytics writes are row-at-a-time. One `INSERT` per event, because pgx's simple protocol will not batch semicolon-separated statements. That is fsync-bound, and it is one to two orders of magnitude off what `COPY` or a multi-row insert reaches on the same hardware. Telemetry is in better shape — a single buffered flusher goroutine does all of that writing, so it cannot open a backend per concurrent flush.

At small and medium traffic this is comfortably fine. The failure mode worth naming is not analytics latency, which nobody watches. It is that at real analytics volume those per-row inserts compete with the app's own transactions for the same WAL and the same shared buffers, so what you *notice* is that your transactional queries got slow.

There are obvious levers here and **Sky does not pull any of them today.** Batching the analytics inserts is the big one. `synchronous_commit = off` on the telemetry connection only would be nearly free, since that setting is per-transaction and the app's own data would keep full durability. Time-partitioned event tables with BRIN indexes, dropping old partitions instead of deleting rows, is the standard answer for append-heavy data. And a connection pooler belongs in the plan earlier than instinct suggests — the numbers above say two eight-core instances, not some distant scale. None of that is implemented. I am listing it so that the shape of the next problem is visible, not so it reads as a feature list.

One more thing an operator should know: nothing splits analytics or metrics onto a separate database automatically. Each component takes a DSN. Same DSN, same database; different DSN, different database. That seam is deliberately unopinionated, and it is where you would separate them when the paragraph above starts describing your app.

## Five rounds, five sets of defects

The part I most want to record is what happened after the code was "done".

Five adversarial review rounds ran against work whose tests were already green. All five found defects. Two are worth naming because the lesson generalises.

The first: `sky db provision --shared` against a PostgreSQL cluster that was already running. Sky writes a hardened `pg_hba.conf`, and writing that file is not applying it — the postmaster read its own copy at startup and goes on enforcing that indefinitely. Against an operator's running `trust` cluster, the tool wrote a correct file, printed **"cluster ready"**, and an app then authenticated with the wrong password, and with no password at all. An adopted `md5` cluster failed loudly, and a cluster sky started itself read the new file, so the only quiet case was the one where quiet is fatal. Provisioning now reloads a running cluster and proves the reload took — `pg_ctl reload` reports success for a reload the postmaster discards — and it asks the server which `hba_file` it is actually using, refusing when that is not the file sky wrote.

The second: the licence gate, which is the thing standing between an Apache-2.0 product and a GPL library inside a shipped binary. It correctly failed a bundle containing GNU readline as a regular file in `lib/`, and passed the identical library shipped as a symbolic link — `find -type f` does not match one and `[ -f ]` follows one — while the link also resolved every dependency on it back into the bundle, so the report cheerfully said "unvendored deps: 0" for a file the bundle did not contain. A bundle's `lib/` is mostly symlinks, because it is assembled with `cp -Rf` to preserve soname chains. So the gate was blind in the common case.

The lessons, both of which I have written down where I will hit them again:

**Assert each property where it lives, not one call short.** The hba writer was correct. A whole round of findings had the same shape: a gate names the right property and then proves it of a function standing one call inside it. "The file is correct" and "the server is enforcing it" are two different statements, and only one of them was being tested.

**An artefact and its own description disagreed, and nothing compared them.** The licence report described a bundle that was not the bundle on disk. Neither did anything wrong on its own; nothing checked that they were talking about the same thing.

The last post said the failure mode I fear most is a green dashboard that means nothing. Five rounds against green tests, five rounds of findings, is what actively hunting that looks like. It is also why grilling every phase is now a step in the process rather than a judgement call about which surfaces look risky — an earlier phase's shell-injection defect was found *incidentally*, by someone doing something else, and eleven commits had landed before the first grill round. Eleven too many.

## What you can actually do with this today

Being precise, because this is where a post like this usually overstates. There is **no published PostgreSQL bundle release yet**. `sky db provision --embed` knows how to fetch, verify and pin one, and at the time of writing there is nothing on the other end of that URL.

What works today: point `SKY_POSTGRES_BIN` at a PostgreSQL you already have, or install from a local archive with `sky db provision --embed --from ./postgres-….tar.gz --checksum <sha256>`, or have a system PostgreSQL on `PATH` and let `sky db start` supervise a per-project cluster on it. Discovery goes in that order, and `SKY_POSTGRES_BIN` set to something incomplete is an error rather than a quiet fall-through to whichever installation the machine happened to have — the typo you made is better than a cluster from an installation you did not choose.

The CI build matrix that publishes the bundles is the remaining piece. When it publishes, `sky db provision --embed` becomes a one-liner, and I will say so then rather than now.

## BlueDB

BlueDB is paused, not cancelled, and I want to be clear about the difference.

The branch is preserved with all of its evidence: the architecture document, the gate harness, the mutation ledger that proves each gate can actually fail, and the status board recording honestly that most goals were never closed. If the demand I could not find today shows up — real serializable pressure from real applications, not an assumption — the substrate research is done and the decision to restart would be made against numbers rather than instinct.

And the research is what made stopping defensible. I did not stop because it got hard. I stopped because six days of building an engine taught me enough about the field to know that the guarantee I was chasing is not available off the shelf under a permissive licence, is not needed by anything I have, and is not what makes a server-driven UI framework good. That is a useful thing to have learnt in six days, and much cheaper than learning it at version 1.

The last post ended by saying the data layer would ship when its gates were green. The gates went red, and the honest response to red gates is sometimes to fix them and sometimes to ask what you were building. I asked. The answer was PostgreSQL, which has been the answer for thirty years. The work worth doing was not replacing it — it was making it something Sky ships and supervises, so that "one language for the whole stack" stops meaning "and then you install a database".
